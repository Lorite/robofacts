# Changelog

## Unreleased

- A documentation site (2026-11-26): https://lorite.github.io/robofacts/, built with MkDocs and Material from `docs/` and published on GitHub Pages by `.github/workflows/docs.yaml` (every push and pull request builds it with `--strict`, a push to `main` publishes it). The long README is split into 52 small pages (getting started, concepts, guides, backends, reference), which link to each other with wikilinks (`[[page]]`, resolved by file name with `mkdocs-obsidian-bridge`, so a broken link fails the build). The reference of the commands, the lint rules and the gate checks is generated from the code by `tools/gen_docs_reference.py`, and `robofacts_ros2/test/test_docs_reference_is_current.py` fails when a committed page is stale. The README now points to the site. `setup.py` names the site as the project's documentation, which the PyPI page shows from the next release. The test that no lab name reaches the packages also scans `docs/`, `mkdocs.yml` and `tools/`.
- The runner's message when an override is set (2026-11-26) said "failures will not block", which was wrong since 0.1.1: it now says that a failed soft item will not block and a failed `[HARD]` item or factor check still blocks.
- The pose pause follows the trial's domain (Alejandro, 2026-11-26): it asked for the word `fly` only when `runner.yaml` said `simulation: false`, while the refusal of a hardware run without a terminal used the trial's domain, which a factor level can set (`domain: {level: hardware}`). Such a level in a `simulation: true` experiment was refused without a terminal and then started on a plain Enter. Now `trial_is_hardware` decides the pause, the spoken GO, the voice defaults and the run marker for the stop tools, which ignored the marker of such a trial as a simulation's.
- The quickstart test started `python3` through a link to `sys.executable`, which loses a venv's packages (2026-11-26). It now uses a small wrapper script.

## 0.1.1 (2026-11-26)

- `robofacts` on PyPI (2026-11-25): `pip install robofacts` installs the general package from PyPI, without a clone. The workflow `.github/workflows/release.yaml` builds the sdist and the wheel of `robofacts/` on every `v*` tag, fails on a `twine check --strict` warning or on a tag that differs from the built version, installs the wheel alone and runs a generated project (lint, plan, one trial, the coverage index), and then publishes through PyPI trusted publishing, so no token is stored in the repository. A manual run builds and checks only. The package has its own README for the PyPI page (`robofacts/README.md`, without middleware names, so the purity test still passes) and the project links, keywords and classifiers. `robofacts_ros2` is not on PyPI, because it needs `rclpy`. Both packages and `CITATION.cff` say 0.1.1.
- pytest is a dependency of `robofacts` (2026-11-25): the linter's rules are pytest tests, so `trials lint` and `trials validate` stopped with `ModuleNotFoundError: No module named 'pytest'` after a plain `pip install` (found by installing the wheel without extras in `python:3.10-slim`). The CI had always installed the `test` extra.
- An MCP server for agents (2026-11-25): `trials mcp` serves nine read-only tools over stdio with JSON results (`list_experiments`, `list_campaigns`, `validate_experiment`, `lint`, `plan_campaign`, `dry_run_campaign`, `coverage_index`, `list_trials`, `explain_trial`), built on the MCP Python SDK 2 as the optional extra `robofacts[mcp]` (module `robofacts.mcp`). No tool runs a trial, runs a gate check against a robot, writes the stop latch or changes a file: the dry run calls the runner with `dry_run=True` and no gate, `validate_experiment` leaves out the experiment's own test files, and the result of a dry run names the `--execute` command for the operator. Arguments are names, never paths, and an argument a tool does not declare is refused. `test/test_mcp_read_only.py` calls every tool on a copy of the example with recorded trials and checks that no file changed, no process other than the lint's pytest started, no socket opened and no stop latch was written, plus a static check of the server's code. The CI job `core-no-ros` installs the SDK through the `test` extra.

### Fixes from the pre-release review (2026-11-25)

Three rounds of independent review before the first PyPI release. Each fix has a test that fails without it.

- The gate (decided on 2026-11-26):
    - No override passes a failed [HARD] item or a factor check that did not pass. Before, `--gate-override` passed both and the trial counted, while the checklist template says that a [HARD] item cannot be overridden and the paper says that a failed check never counts. A failed soft item may still be overridden with its reason, and the shadow mode of a `gate` factor (simulation only) still records every verdict and never blocks.
    - A hardware trial runs only after a T-0 gate. Before, an experiment without a gate checklist, or the web interface's "skip the gate", ran a hardware trial with a warning only. A simulation still runs ungated, with the UNGATED warning.
    - A hardware run whose stdin is not a terminal is refused unless `--no-pause` is given, because nobody could type `fly` at the pose pause. Before, the pose pause and the operator steps passed without a word. Without a terminal, the operator steps are now printed with a line that says that nobody waited for them. The web interface answers the pose pause in the browser and needs no terminal.
- The runner and stops:
    - The trial's action ends before the teardown. On Ctrl-C the runner stopped the recorder and the stack while the action was still landing. Now the interrupt goes on to the action, the runner waits up to 90 s for the action's whole process group to end (a flight lands), and only then sends SIGTERM and SIGKILL. A second Ctrl-C kills it at once.
    - SIGTERM and SIGHUP take the Ctrl-C path. Before, they ended the runner at once and left the stack and the recorder running, with no metadata and no ledger line. A second interrupt during the teardown waits until the recorder and the stack have stopped.
    - A local action leads its own process group, so the action timeout and the web interface's stop reach the whole action, also behind a wrapper script and a flight that the wrapper started in the background. After a normal exit, a process that the action leaves running is named in a warning and the trial keeps its result (a daemon that a tool of the action starts is normal). After a stop or a timeout, the runner still waits for the whole group to end before it stops the stack. A local action has no terminal, so it must not prompt (the skeleton's `runner.yaml` says so).
    - A closed terminal lands the action and stops the stack. After a hangup every write to the terminal failed, and an unguarded print broke the stop path, so the stack and the recorder ran on and the trial had no metadata.
    - Ctrl-C at the web interface's server lands the action of the running trial and waits for its teardown. Before, the server exited with the action still flying. SIGTERM and SIGHUP take the same path (a `pkill`, a service manager or a closed terminal ended the server at once), and a second Ctrl-C during the landing exits at once, as the server says.
    - A stop from the web interface during the settle time, the gate or the pose pause is no longer lost: the trial ends before the recorder, the action or the manual window starts. Before, the recorder started, the action flew, and the trial was written as complete. An action that a stop ended never counts, also when it lands and exits 0.
    - A stop ends the manual window of a trial whose action step is disabled, and that trial is aborted. Such a trial now records `steps_disabled`, which `trials records` shows.
    - An error after the recording (a verify step that cannot run, a full disk) writes the trial as aborted with a ledger line. `trial_metadata.json` and `recording.json` are written whole (a temporary file, then a rename), and a failed metadata write fails the trial on record.
    - One run per project: an executed run is refused while another live run holds the project's run marker (from the CLI and from the web interface), two attempts in the same second get two directories, and a runner removes only its own marker. After a runner was killed with `kill -9`, the next run refuses while that run's processes still run, prints the commands that stop them, and puts the killed trial on record as aborted. A dead runner's marker no longer blocks `exclude`, `amend` and `reverify`. A refusal ends `trials run` with its message and exit code 1. After a container restart or a reboot, the pid in a marker can belong to another process: the marker now records when its process started, so such a pid no longer refuses every run for 12 hours.
    - After a runner was killed during a remote trial, the next run says that the stack and the recorder may still run on that host and prints the clean-up to run there (a backend names its clean-up tool in the new field `clean_slate_tool`). Before, the refusal printed a `kill` that stops only the local ssh clients.
    - Every command of a planned run, the launch command included, is rendered before the first trial starts, and `trials validate` reports a command that cannot be rendered. A placeholder typo in a verify step stopped the run only after a trial had flown and recorded.
    - Each placeholder value stays one argument: a project folder with a space in its name aborted every trial, and a level with an apostrophe raised an error. A list value that is a whole argument, such as `{bags}` of an analysis, still becomes one argument per element, and inside a larger argument its elements are joined with spaces.
    - A trial id is cut on UTF-8 bytes, not characters: a long level in Chinese characters made a directory name the file system refused, and `trials records` then stopped for the whole experiment. It now lists such an entry.
    - `trials run` counts a trial whose metadata breaks the experiment's contract apart from the OK ones ("recorded but unverified") and names its first problem. Before, it said OK for a trial that never counts.
    - An action that could not start, or that the runner lost (a byte that is not UTF-8 in its output), is written as aborted and never counts. Before, it was written with `aborted: false` and counted as coverage, and the lost action ran on into the next trial.
    - An action that a signal ended is reported as "interrupted (SIGINT)", "stopped (SIGTERM)" or "killed (SIGKILL)", not as "the trial did not happen as planned". The abort reason names the signal and the stage the trial had reached (it named the teardown before), and an interrupted run ends with one line and the exit code 128 plus the signal number instead of a traceback.
- The emergency stop (`trials tool estop.sh`):
    - Every documented form of a robot's stop command runs whole: the string form that the skeleton `robots.yaml` documents crashed the reader, and only the first line of a multi-line command ran, while the script still said "All robots confirmed the estop" with exit 0. A stop entry it cannot use now counts as a failed stop (exit 1), and the other robots still get theirs.
    - A local container with the robot container's name no longer takes the robot's stop when its hostname differs from the declared `container_hostname`. The stop goes over ssh to the declared host. The lab's routes are unchanged.
    - Inside the robot's own container, the stop runs in the declared login shell of the host level (`zsh -lc` in the lab), as `robot_action.sh` does. Before, it ran in `bash -c`, so a container that sets its middleware configuration only in the shell's startup files sent the stop without discovery and could still report OK.
- The Crazyflie example: the hover lands on SIGHUP and SIGQUIT as on SIGTERM (a closed terminal ended it without a landing), an operator stop during the landing aborts the trial, and the verify step fails a flight that ended in an emergency stop.
- The `process` backend's recorder runs with the Python interpreter that runs `trials`. With `pipx`, or a virtual environment that was not activated, the `python3` on the PATH had no robofacts, and every trial recorded nothing.
- Settings: `names()`, `default_record_profile()`, `default_cf_name()` and the adapter functions read `trials.yaml` from the working directory, not from the experiments root they were given. A run started inside another project read that project's adapters and blocked every trial. They now take the experiments root, a setting read without one follows `$TRIALS_EXPERIMENTS_ROOT`, and `trials run` and `trials ui` export their root. The project root of a given experiments root comes from that project's `trials.yaml`, also in `trials roots`.
- The linter:
    - L10 checks the metadata contract's invariant (every swept factor is recorded as a coverage axis), as the paper says. Before, only `plan`, `check` and `run` refused such a campaign.
    - The lint ignores the pytest configuration and the `conftest.py` files of the project it checks. With robofacts installed in a virtual environment inside the project, the project's `conftest.py` ran during `trials lint` and during the MCP server's `lint` tool.
- Campaigns: a sweep that lists a level twice is refused (it doubled the trials wanted of that level). Levels such as `1` and `true` are not duplicates.
- The coverage index and the records:
    - The grid shows the axes that vary before a constant one, and its "also varying" note names only axes that vary.
    - With recordings on a disk that is not mounted, `trials plan`, `trials run`, the web interface's plan pages and the MCP server's plan stop with the disk to mount. Before, the plan read those trials as missing cells, and a run would have recorded them again. `trials run` checks the disk before it prints the plan.
    - `trials metadata` audits the trials that the index reads (with only slim copies present it found none), and `trials reverify` renders the verify steps with the corrected factor values.
    - `trials records` reads a run log the same way on Python 3.10 to 3.14 (the core suite failed on 3.14).
    - `trials records` marks its start times as UTC (`started` in `--json` ends in `Z`).
- The web interface:
    - An EXECUTE gets the CLI's T-0 gate from the campaign's checklist when the experiment has no `scripts/preflight.sh`. Before, such a run had no gate and its trials counted. A run without any gate says UNGATED.
    - A dry run no longer takes the rig's single run slot, so the stop reaches the executing run. The interface starts one run at a time, a dry run too: two runs at once mixed their logs.
    - A POST action that a page of another site sent is refused, and a campaign field can no longer name a file outside the experiment's `campaigns/`.
    - The stop and robot action buttons use the `robots.yaml` of the interface's project, not one found from the server's working directory.
    - With a password, a slim bag's URL for the viewer carries a token (`?t=`), and a bag URL without it is refused. The token is keyed with a random secret that the server makes when it starts, not with the password: anyone who saw one link could test passwords offline, and the viewer link goes to app.foxglove.dev. The links of a page opened before a restart of the server stop working.
    - Kill ROS uses each host's checkout and setup files from `hosts.yaml`. Before, it ran `cd` into the interface's own checkout on the rig.
    - The clean slate no longer fails with an error while a trial runs, an undeclared host in the gate button answers 400, and the `back` field of a form only leads back into the interface.
- `trials tool robot_action.sh` runs every documented form of an action whole and follows the `container_hostname` rule, as `estop.sh` does.
- The ROS 2 backend:
    - Explore's action runs while any process of its group lives: a wrapper that started the flight in the background and exited freed the action slot, Stop said that no action was running, and the shutdown stopped the stack under the flying robot. Stop and the shutdown now reach the whole group and wait for the landing.
    - A stop reaches the remote stack after its ssh client has exited (a lost Wi-Fi). Before, the remote `pkill` never left.
    - The remote slim copy runs from the `robofacts_ros2` package. Outside the lab, every remote trial got no slim copy.
    - The slim copy of an externally recorded bag stays in the repository's `bags_slim/`, not on the external disk.
- The MCP server: a factor level that contains a comma is refused (it became a sweep of two levels), and `trials mcp --help` works without the MCP SDK.
- Packaging: the license text is in the wheel and the sdist, the sdist no longer ships a test suite that cannot run, the classifiers name Python 3.10 to 3.14 and the CI job of the general package runs on each, the release workflow runs the core suite before it publishes, and every action of the release workflow is pinned to a commit. `colcon build --symlink-install` builds `robofacts` again: its `setup.py` looked for the PyPI page's README next to the symlink that colcon runs, not next to the file.
- Docs and examples: the PyPI page names the MCP extra, the README gives `rosdep install ... --skip-keys robofacts` (rosdep has no rule for `robofacts`), the CLI's help no longer names a tool that only the ROS 2 backend ships, the stand-in systems of the examples stop quietly on SIGINT, and the README steps that run `--execute` on a demo pass `--no-pause` or say that each trial waits for Enter. The help and the messages name the backend's own folders, the usage line of each subcommand names the subcommand, `trials new --from` names only the files that the copy has, a NO-GO with a failed [HARD] item says to fix the cause, the Dockerfile's test command runs in the quickstart image, and the README names Python 3.10 to 3.14 for the job without ROS.
- Tests: the web interface's tests no longer skip the whole ROS 2 suite when Flask is missing (a module-level `importorskip` collected 0 of 527 tests with exit code 0), and a static check refuses that pattern in every test module. The redirect test of the web interface passes with the Flask 2.0 of Ubuntu 22.04, which the Humble CI job installs.

## 0.1.0 (2026-11-25)

The framework of a robotics lab's experiments, extracted into two installable packages: `robofacts` (Python only, `pip install`) and its ROS 2 backend `robofacts_ros2` (`ament_python`).

- Prepared for the public release (2026-11-25): `studies/sac2027/` holds the pre-registration files of the SAC 2027 studies (predictions, protocols and deviation logs), verbatim from the laboratory repository, with a README that maps each file to its study and gives its commit date against the start of the main run. The README now starts for a first-time reader (what RoboFACTS is, install, quickstart, the three examples, how to cite), and `CITATION.cff` cites the SAC 2027 paper. Laboratory issue numbers, LAN addresses and host names were removed from code comments, docstrings and tests (the addresses became RFC 5737 documentation addresses). The cflib example arms through `supervisor.send_arming_request`, because cflib deprecated `platform.send_arming_request`, and a test checks it.
- A Crazyflie example without ROS 2 (2026-11-25): `examples/cflib_hover` is its own project on the `process` backend. One Crazyflie hovers on its Flow deck, commanded with cflib: the action refuses before arming on a fresh stop latch, a missing Flow deck, a low battery, an unsettled estimator or a ground position away from the origin, takes off in two stages, and lands on the end of the hover, on a signal, on the stop latch, at a geofence and on any error (an `estop` latch cuts the motors). The gate reads the battery and the Flow deck over the radio with two checks of the project, the drone's reset is a power cycle over the radio, and the verify step reads the recorded height. Its tests need no drone and no radio (a fake drone for the hover logic). Neither package changed for it.
- README section "What a backend must provide" (2026-11-25): the required launcher and recorder with each method, the optional fields of `Backend` with their defaults, and the two shipped implementations as examples.
- `backend:` in `trials.yaml` is required (2026-11-25): there is no default backend. Without the line every command stops with the line to add (`$TRIALS_BACKEND` still overrides for one session). `trials init` writes it, `process` unless `--backend` names another. A project of the ROS 2 package adds `backend: ros2`.
- The folders of an experiment are named by the backend (2026-11-25): on the `process` backend `recordings/`, `recordings_issues/`, `recordings_slim/`, `recordings_issues_slim/`, `recordings_scratch/` and `recordings_scratch_slim/`, on the ROS 2 backend the `bags*` folders as before (`Backend.record_dirs`, `backend.record_dirs()`). The coverage index, the decisions about a trial (`trials exclude`, `restore`, `amend`), the metadata audit, `trials records`, the runner, the scaffolding and the web interface read the names from there. `--recordings-root` is a second name of `--bags-root`, and `recording_dir_writable` a second name of the check `bag_dir_writable` (no new script, so the core still ships 8 checks). The record fields `bag_storage` and `bag_dir` keep their names. The example and the experiment template of the general package use the new names. A copy with `trials new --from` leaves out the recording folders of both schemes.
- The web interface is general (2026-11-25): `trials ui` and its pages are part of `robofacts` (Flask as the optional extra `robofacts[ui]`). A backend extends the interface through its feature `ui` (`TEMPLATES`, `template_globals()`, `layouts()`, `register(ui)`), and its `_viewers.html` replaces the general one. The ROS 2 backend's extension, `robofacts_ros2.ui_extension`, adds the Foxglove replay links and layouts, the Viewing page, the slim-bag download for the viewer and the clean slate of the rig hosts. Explore is offered only when the backend has the feature `explore`. On the lab's data, served read-only, the pages of the interface are the same before and after, apart from six reworded tooltips and hints.
- An example without ROS (2026-11-25): `robofacts/example_project` holds one experiment on the `process` backend, `demo_log_recorder`. A script stands in for the system under test and appends lines to a log file, the recorder stores what it writes during a trial, a verify step reads the recording, and the campaign `grid` sweeps two factors (`rate`, `duration`), so the coverage index shows four cells. `robofacts/quickstart.sh` runs the loop on it from the linter to the coverage index, and the CI job `core-no-ros` runs that script on `python:3.10-slim` with only `robofacts` installed. The core's tests run against this example, never against a project that lies above the working directory, and they need neither git nor `pgrep` (the tests of the code version are skipped where git is absent).
- Two packages (2026-11-24): the repository holds `robofacts/` (the general package: declarations, planner, linter, coverage index, the trial loop, the gate protocol with 8 general checks, the launcher and recorder interfaces, the `process` backend) and `robofacts_ros2/` (the ROS 2 backend: launcher, bag recorder, bag readers and slim copy, 13 ROS 2 gate checks with their sentences and concurrency classes, the robot adapters, the ROS 2 lint rules L2, L5, L11 and L16, Explore, the web interface, `kill_ros.sh`, the talker template). `robofacts` has no `package.xml` and depends on PyYAML only. `robofacts_ros2` depends on it. `robofacts/test/test_core_is_free_of_ros.py` fails the build when the general package imports a ROS module, names ROS in any file, or loads a ROS module on import. What changes for a project: (1) `trials.yaml` names the backend, `backend: ros2`, and without the key a project runs on `process` (a ROS 2 `launch:` block is then refused with the line to add). (2) The command is `trials` (on the PATH after sourcing a colcon workspace, or after pip) or `ros2 run robofacts_ros2 trials`. `ros2 run robofacts trials` no longer exists. (3) Modules that moved are imported from `robofacts_ros2`: `bag_io_utils`, `slim_bag`, `slim_bag_archive`, `export_rosout_text`, `explore*`, `pose_sample`, `ui`, the adapters (`robofacts_ros2.adapters.<name>`), the bag-reading half of `trial_media`, and `build_record_command` and the heavy-topic rules of `record_profiles` (`robofacts_ros2.record_profiles` re-exports the rest). (4) A check script that sources the helper file by a path of the old layout needs the new path (`$PF_LIB` is unchanged when the gate runs it). (5) `colcon_workspaces` is still read on the ROS 2 backend, `build_workspaces` is the general key. `trials init --backend ros2` writes a ROS 2 project. The dry-run commands, record topics, gate checklists, stop patterns and lint results of a robotics lab's 118 campaigns are identical before and after, apart from the paths of the moved modules.
- Backends (2026-11-24): the trial loop no longer names ROS 2 where it starts the stack and records the trial. `robofacts/backend.py` defines two interfaces that return command lines, a `Launcher` (`parse`, `command`, `stop_patterns`) and a `Recorder` (`command`, `has_data`, `holds_data`, `unsettled_reason`, `after_trial`, and `noun`, the word for one recording), and a `Backend` object that holds them with two optional hooks (the default setup files of a host, a step before the gate's machine checks). `trials.yaml` names the backend with `backend:`, `$TRIALS_BACKEND` overrides it, and a project that names none runs on `ros2` as before. The ROS 2 code is behind the interfaces in `robofacts/backends/ros2/` (`ros2 launch`, `ros2 run`, `ros2 bag record`, the completeness test of a bag, `rosout.txt`, the slim copy, the daemon restart before a gate). `robofacts/backends/process.py` is a second backend without any middleware: `launch: {command: ...}` starts the stack, and `python3 -m robofacts.backends.process_recorder` stores what the system appends to the files of `record_sources` during the trial, finalized by `recording.json`. `record_sources` is a second spelling of `record_topics` in `runner.yaml`. The process backend refuses `launch.package` and `launch.file` with the line to add to `trials.yaml`. Commands, record topics, gate checklists and stop patterns of a robotics lab's 118 campaigns are identical before and after.
- Lint rule L6 binds every experiment (2026-11-24): `runner.yaml` declares at least one verify step, or a written reason why it has none (`no_verify_steps: <reason>`). Before, the rule looked for flight words in the action and in the factor levels, so only an experiment that flies had to check its recording, although a ground robot whose action exits 0 while it stands still produces the same false trial. The lint cannot know from a declaration what moves, so it asks every experiment and accepts a reason. Both keys together, or a reason that is not a sentence, fail the rule. The example experiment now has a verify step (`scripts/verify_chatter.py`, at least 3 recorded messages), as the generated experiment already had.
- One host registry (2026-11-16): `common/config/hosts.yaml` declares how to reach each `execution_host` level once (`local`, or `host`, `container`, `container_hostname`, `shell` and the setup files), and an experiment's `runner.yaml` `hosts:` lists its levels and writes only what differs (`host_registry.py`). A robotics lab had 18 full copies of these settings, and one level had drifted to three ssh aliases, two of which did not reach the robot computer on the lab's network. `RIG_HOST` replaces the ssh alias of the registry's `rig:` level, the same variable `estop.sh` reads. A trial on a level that its experiment does not declare is now refused instead of running on the runner's own machine. A project without `hosts.yaml` works as before.
- The stop follows the trial (2026-11-16): a robot in `robots.yaml` names a `host_level`, resolved through `hosts.yaml` (`host_registry.robot_targets`). The runner notes each trial's `execution_host`, robots and simulation flag in its run marker (`run_marker.note`), and `estop.sh` and `robot_action.sh` send a hardware trial's robots to its host. `--host-level` overrides for one call. A simulation never moves a stop, and a marker whose runner process is gone is ignored (`run_marker.read_live`). `estop.sh --list` and the stop output name each robot's host and the reason, the runner prints the targets at the start of every hardware trial, and the web interface's clean-slate button resolves its hosts the same way. Before, a trial on the laptop sent the stop to the robot computer unless the operator remembered `RIG_CONTAINER`.
- A stop typed inside a container runs there only when it is the target's own container (2026-11-17): `container_hostname` of the host level must match the current hostname. Before, any container counted, so a stop typed in a laptop's container for a stack on the robot computer stayed on the laptop. `robot_action.sh` follows the same rule (it had no container check and tried `docker exec` inside a container). `estop.sh --list` prints a `route:` line per robot, and the runner's line says `here, in this container` when that is the route. `TRIALS_DOCKERENV` lets tests point the container check at a file of their own.
- The core names no robot and no lab (2026-11-09): `test/test_core_names_no_robot.py` fails the build on a robot family or a lab name in a core file, with a short allowlist for facts about third-party tools, and on internal issue numbers anywhere in the package. The comments, docstrings and docs lost the issue numbers and the lab's robot, rig and experiment names, and keep the reason and the date of each lesson. What a slim bag drops is the core's generic image, depth and point-cloud patterns plus the project's `slim_topics: {heavy_patterns, light_suffixes}` in `trials.yaml` (a lidar's clouds and a debug overlay used to be core rules), and `HEAVY_TOPIC_PATTERNS` resolves on access. `pose_error_analysis` left the package (its rows are one project's data format), and its `PoseSample` record is `robofacts.pose_sample`. The defaults of `camera_frames` (`topic=/camera/color/image_raw`) and `ros_clean_slate` (`pattern=component_container`) no longer name one lab's devices, and the web interface reads a lease table from any enabled adapter that offers `LEASE_TABLE`.
